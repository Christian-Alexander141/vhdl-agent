Softwaredokumentation

Historische Übersicht: Die frühere RAG-Pipeline wurde entfernt. Alle Sprachmodell-Aufgaben laufen über OpenCode (Planung samt Namensvergabe, HDL, Testbenches, Referenzmodelle, Reparaturen, Chat-Antworten). Die frühere Ollama-Anbindung wurde am 2026-10-10 entfernt (Abschnitt 15, #22).

1. Architekturüberblick

Die Plattform verwendet eine hexagonale Architektur mit klar getrennten Schichten:

  • Domain Layer: Kernlogik, Zustandsautomat, Domänenmodelle und Port-Interfaces.
  • Service Layer: Implementierungen von Ports, die konkrete LLM-, RAG-, Artefakt- und Dateisystemdienste bereitstellen.
  • Orchestrator / Workflow: Steuerung des Task-Lebenszyklus und Ausführung des Hauptworkflows.
  • API / CLI: Schnittstellen für Benutzer, Dashboard und asynchrone Task-Ausführung.

2. Konfiguration

Die Konfiguration wird von Schaltungsagent/src/config.py über config.yaml geladen.

Wichtige Konfigurationsbereiche:

  • llm: Provider, Modell, Base-URL, Temperatur und Token-Limit.
  • rag: Vektorspeicher, Embedding-Modell, Chunking und Datenverzeichnis.
  • workspace: Basisverzeichnis der Tasks, Cleanup-Strategie und Maximallimit.
  • opencode: Pfad zur OpenCode-Binärdatei, Timeout und Reparaturversuche.
  • dashboard: Host, Port und WebSocket-Pfad.
  • domains: Standarddomain und Suchpfade für Domänenmodule.

3. Einstiegspunkte

3.1 CLI

Schaltungsagent/src/main.py ist das zentrale CLI-Skript. Es lädt die Konfiguration, erstellt Services und den Orchestrator und bietet folgende Kommandos:

  • run <request>: Führt eine neue Task aus.
  • list: Zeigt bestehende Tasks aus dem Workspace-Verzeichnis.
  • show <task_id>: Zeigt den Task-Zustand an.
  • file <task_id> <filename>: Gibt eine generierte Datei aus.
  • discover: Entdeckt Domains im Projekt.
  • serve: Startet den FastAPI-basierten Server.
  • rag: Startet den interaktiven RAG-Chat.

3.2 API Server

Schaltungsagent/src/api_server.py initialisiert den HTTP-Server, öffnet WebSocket-Verbindungen und stellt REST-Endpunkte bereit.

Wichtige Endpunkte:

  • GET /: Dashboard-Seite.
  • GET /api/tasks: Listet laufende und abgeschlossene Tasks.
  • POST /api/task: Queued einen asynchronen Task.
  • POST /api/task/sync: Führt einen Task synchron aus.
  • GET /api/domains: Liefert verfügbare Domains.
  • POST /api/cleanup: Löscht abgelaufene Arbeitsverzeichnisse.
  • GET /ws: WebSocket für Ereignisbenachrichtigung.

4. Domain Layer

Der Domain Layer definiert Schnittstellen und Zustände ohne konkrete Implementierung:

4.1 Workflow State Machine

Schaltungsagent/src/domain/state_machine.py enthält die möglichen Workflow-Zustände:

CREATED → ANALYZING → RAG_SEARCH → GENERATING_ARTIFACTS → WORKSPACE_READY → RUNNING_AGENT → TESTING → VALIDATING → COMPLETED

Fehlerpfade führen zu FAILED. Zusätzlich erlaubt TESTING den Übergang zu REPAIRING, von dort zurück zu RUNNING_AGENT oder zu FAILED.

4.2 TaskState

Schaltungsagent/src/domain/models/task_state.py beschreibt den Task-Zustand mit folgenden Feldern:

  • task_id: UUID der Task.
  • status: Aktueller Workflow-Zustand.
  • request: Benutzeranforderung.
  • domain: Ziel-Domain (z. B. VHDL).
  • workspace: Pfad zum erzeugten Arbeitsverzeichnis.
  • generated_files, artifacts, test_results, history, metadata.

Die Methode add_log() erweitert den Verlauf, set_status() aktualisiert den Zustand.

4.3 Ports

Schaltungsagent/src/domain/ports/ definiert abstrakte Schnittstellen:

  • LLMService: Analyse, Codegenerierung und Ergebniszusammenfassung.
  • RAGService: Wissensrecherche und Rückgabe von KnowledgeBundle.
  • ArtifactGenerator: Erzeugt ArtifactBundle aus Anfrage, Analyse und Wissen.
  • FileSystemService: Erzeugt Workspaces, schreibt und liest Dateien.
  • OpenCodeService: Führt OpenCode-Aufgaben im Workspace aus.
  • EventPublisher: Veröffentlicht Ereignisse.
  • PlannerService: Optionaler Planer für Task-Ausführung.
  • ValidationService: Optionaler Validator für Testergebnisse.

5. Orchestrator & Workflow

Der zentrale Orchestrator befindet sich in Schaltungsagent/src/orchestrator/supervisor_orchestrator.py und verwendet den LangGraph-Workflow.

Die Hauptfunktionen:

  • execute(): Führt eine Task sequenziell aus.
  • execute_async(): Startet einen Hintergrundthread und übergibt beim Abschluss optional ein Callback.
  • get_task_status() und list_tasks(): Liefern Informationen über laufende Tasks.

5.1 Aufbau des Workflows

execute() führt in dieser Reihenfolge aus:

  1. Analyzing: Analyse der User-Anfrage durch LLMService.analyze_request().
  2. RAG Search: Wissensrecherche über RAGService.retrieve_knowledge().
  3. Generating Artifacts: Erzeugung von Artefakten durch ArtifactGenerator.generate().
  4. Prepare Workspace: Erzeugung einer Task-spezifischen Arbeitsumgebung und Schreiben aller Artefakte.
  5. Running Agent: Ausführung von OpenCode oder dem optionalen Planner.
  6. Testing/Repairing: Validierung und ggf. automatische Reparatur.
  7. Validating: Abschlussvalidierung und Zusammenfassung.

5.2 Fehlerbehandlung

Der Orchestrator fängt spezifische WorkflowError-Unterklassen und allgemeine Exceptions ab. Bei Fehlern wird der Status auf FAILED gesetzt und der Fehler dokumentiert.

Ereignisse werden während des Workflows über den EventBus veröffentlicht, z. B. TASK_CREATED, ANALYSIS_STARTED und STATE_CHANGED.

6. Service Layer

6.1 Sprachmodell-Aufgaben (OpenCode)

Es gibt keinen eigenen LLM-Dienst mehr. Sprachmodell-Aufgaben laufen über den OpenCodeService (Abschnitt 6.5):

  • Planung und Namen: OpenCode schreibt plan/manifest.json einschließlich project_name und Entity-Namen. Schaltungsagent/src/services/name_resolver.py bereinigt ungültige Namen nur noch deterministisch (z. B. task04-sram → sram) und leitet notfalls einen Ersatznamen ab; ein Lauf scheitert nicht mehr an der Namensvergabe.
  • Projektfragen im Chat: Schaltungsagent/src/services/project_chat.py (OpenCodeProjectChat) lässt OpenCode die Frage im Projektordner beantworten. Es liest dabei den echten Code und den Zustand; der Auftrag ist lesend, Dateiänderungen werden gemeldet.

6.2 RAG-Service

Schaltungsagent/src/services/rag_service.py bietet die Domänen-gestützte Wissensrecherche über VHDLRAGService.

Die Implementierung kombiniert:

  • Domänenspezifische Daten und Vorlagen aus src/domains/vhdl.
  • Keyword-Matching auf Anfrage zur Template-Erkennung.
  • Vector Retrieval über RAGChatPipeline.

Ergebnis ist ein KnowledgeBundle mit Regeln, Referenzdesigns, Dokumentation und Rohkontext.

6.3 Artifact Generator

Schaltungsagent/src/services/artifact_generator.py generiert VHDL-Artefakte.

Workflow:

  1. Suche nach einem passenden Template anhand von Wissen und Anfrage.
  2. Falls gefunden: Verwende Domänen-Templates aus src/domains/vhdl/templates.py.
  3. Falls kein Template passt: Liefere ein Fallback-Resultat ohne generierte Dateien.

Beispiele für Template-Erzeugung sind Counter- und Hamming-Designs inklusive Testbench.

6.4 FileSystem Service

Schaltungsagent/src/services/filesystem_service.py verwaltet lokale Task-Workspaces.

Wichtige Funktionen:

  • create_workspace(): Erzeugt Task-Ordner inklusive Standardunterverzeichnissen.
  • write_file() / read_file(): Umgang mit Dateisystemoperationen.
  • list_files(): Listet generierte Dateien auf.
  • cleanup_expired(): Entfernt alte Workspaces basierend auf TTL.

6.5 OpenCode Service

Schaltungsagent/src/services/opencode_service.py führt externe OpenCode-Prozesse aus.

Die Ausführung erfolgt über subprocess.run() mit Timeout und Rückgabewerten.

  • Im Fehlerfall wird eine AgentExecutionError ausgelöst.
  • Timeouts und fehlende Binärdatei werden abgefangen.

7. RAG Pipeline und Dokumentenindex

Schaltungsagent/src/services/rag_pipeline.py implementiert die Vektorsuche und den Chat-Speicher.

Schritte:

  1. Embedding-Ladefunktion: get_embeddings() lädt HuggingFace-Embeddings.
  2. Qdrant-Initialisierung: get_vector_store() erstellt oder öffnet einen lokalen Qdrant-Store.
  3. Dokumentenladung: load_documents_from_directory() liest unterstützte Quellen.
  4. Indexierung: index_documents() erstellt Chunks und speichert sie in Qdrant.
  5. Ähnlichkeitssuche: retrieve_context() gibt relevante Inhalte zurück.
  6. Chat-Sitzung: create_chat_session() und append_exchange() verwalten soul.md-Memory.

8. Eventbus und WebSocket-Integration

Schaltungsagent/src/domain/event_bus.py stellt einen einfachen Ereignisbus zur Verfügung.

Funktionen:

  • on_event(listener): Registriert einen Listener.
  • emit(): Sendet ein Event an alle Abonnenten.
  • get_events(): Liefert das Event-Log.

Der API-Server registriert den WebSocket-Broadcast als Listener, so dass Browser-Dashboards Live-Updates erhalten.

9. Domänenlayer: VHDL

Die Domain-spezifische Implementierung liegt unter Schaltungsagent/src/domains/vhdl.

  • rag_data.py: Regeln, Referenzdesigns und Template-Zuordnung.
  • templates.py: Jinja2-Vorlagen für VHDL-Entitäten und Testbenches.
  • prompts.py: System-Prompts für die LLM-Anfragen.
  • test_definitions.py: Definitionen für GHDL-Testläufe.
  • build_definitions.py: Build-Konfigurationen für VHDL-Projekte.

10. API / RAG Router

Schaltungsagent/src/api/rag_router.py stellt REST-Routen für den RAG-Chat bereit.

Der Router kapselt:

  • Healthcheck
  • Query-Aufrufe für einfachen Chat, Tool-Einsatz und Planner-Einsatz
  • Session-Erstellung
  • Dokumenten-Upload und Indexierung
  • Modellabfrage

11. Fehler- und Zustandsbehandlung

Die zentrale Fehlerbehandlung ist im Orchestrator implementiert. Typische Fehlerklassen befinden sich in Schaltungsagent/src/domain/exceptions.py.

Designprinzipien:

  • Jede Workflow-Phase meldet Fehler als spezifische Ausnahme.
  • Der Status wird auf FAILED gesetzt.
  • Ergebnisse und Fehler werden im Task-State gespeichert.
  • Workspace-Daten werden jeweils persistiert.

12. Datenablage und Workspace-Layout

Der FileSystem-Service erstellt pro Task ein Verzeichnis unter projects/. Die Standardstruktur ist:

  • src/
  • tests/
  • docs/
  • build/
  • logs/
  • reports/

Am Ende des Workflows wird der Task-Zustand als state.json im Workspace gespeichert.

13. Erweiterbarkeit

Die Architektur ist modular gestaltet:

  • Neue Domains können unter src/domains ergänzt werden.
  • Neue Service-Implementierungen können zusätzliche Port-Schnittstellen erfüllen.
  • Der Orchestrator kann zusätzliche Workflow-Schritte oder Prüfschichten integrieren.
  • API und Dashboard können um weitere Endpunkte und Ereignisse erweitert werden.

14. Zusammenfassung

Die Plattform besteht aus einer zentralen Steuerung, die Aufgaben analysiert, Wissen recherchiert, Artefakte generiert, Workspaces vorbereitet, Agenten ausführt und Ergebnisse testet.

Die klare Trennung von Schnittstellen (Ports) und Implementierung erlaubt Testbarkeit und Austauschbarkeit von LLM-, RAG- und Ausführungsdiensten.

15. Analyse: Warum das MAS hinter einem einzelnen OpenCode zurückblieb (Stand 2026-10-08)

Ausgangslage: Das Multi-Agenten-System (MAS) soll VHDL-Projekte umsetzen, die ein einzelner OpenCode-Lauf nicht schafft. Tatsächlich scheiterte es an Projekten, die OpenCode allein löst. Die Ursachen wurden per Code-Analyse der Pipeline (Plan → Architektur → UART-Integration → Modul-Worker → Gates → Reparatur) ermittelt. Wie oft welche Ursache zuschlägt, ist noch nicht gemessen; dafür gibt es jetzt den Benchmark aus 15.3.

Projektentscheidung: Bis nachgewiesen ist, dass das MAS einem einzelnen OpenCode mit demselben Modell überlegen ist, laufen alle OpenCode-Agenten nativ (opencode.test_mode: true). Die Docker-Isolation für den Produktivbetrieb bleibt im Code erhalten, wird aber erst danach wieder aufgenommen.

15.3 Vergleichsmessung MAS vs. einzelnes OpenCode

Der Benchmark führt jeden Prompt aus Schaltungsagent/benchmark/prompts/*.md in drei Varianten aus, alle nativ, mit dem in opencode.model eingestellten Modell und ohne Synthese:

  • single: ein OpenCode-Lauf auf dem ganzen Projekt. Er kennt dieselben Testbench-Regeln wie die MAS-Worker.
  • mas: MAS mit modularer Implementierung.

16.2 Maßnahme A: Differentieller Test gegen ein ausführbares Python-Referenzmodell

Idee: Neben der VHDL-Implementierung entsteht eine zweite, unabhängige Auslegung der Spezifikation als kleines Python-Programm. Beide werden mit denselben Eingangsfolgen betrieben und Takt für Takt verglichen. Sprachmodelle sind in Python deutlich sicherer als in VHDL; die Erwartungswerte entstehen durch Ausführen des Modells statt durch Schätzen.

Ablauf im MAS:

  1. Modell erzeugen, bevor VHDL existiert (Beginn der Phase IMPLEMENTING). Der VerificationAgent beauftragt OpenCode, aus PROMPT.md und dem typisierten Port-Contract des Top-Levels model/reference_model.py und model/test_reference_model.py zu schreiben. Weil zu diesem Zeitpunkt kein Entwurf vorliegt und der Auftrag das Lesen von src/ untersagt, ist das Modell unabhängig vom Entwurf. Der Selbsttest (mindestens drei test_-Funktionen aus der Spezifikation) muss bestehen.
  2. Schnittstelle (fest vorgegeben): class ReferenceModel mit reset() und step(inputs) -> outputs; optional SUGGESTED_CYCLES. Getaktet: step() erhält die Eingänge vor einer steigenden Flanke (ohne Takt, mit Reset) und liefert alle Ausgänge unmittelbar danach. Kombinatorisch: Ausgänge zu den Eingängen. Bits als 0/1, Vektoren als ganze Zahl.
  3. Vergleichs-Testbench vor jedem Static Check (deterministisch, ohne Sprachmodell): Ports aus der tatsächlichen Entity, Breiten mit aufgelösten Generics. Dann eine Reizfolge:
    • getaktet: Reset in den ersten beiden Takten und bei 60 %; die übrigen Eingänge werden über zufällig lange Abschnitte gehalten, damit Zähler und Zeitgeber ihre Endwerte erreichen;
    • kombinatorisch: bis 12 Eingangsbits vollständig, sonst zufällig.
    Das Modell läuft in einem eigenen Prozess mit Zeitlimit und berechnet die Erwartungswerte. Daraus entsteht tests/<top>_model_tb.vhd mit eingebetteten Vektoren (keine Datei-Ein-/Ausgabe, keine Pfadabhängigkeit). Abtastung wie bei den gegen Mutanten geprüften Referenz-Testbenches des Benchmarks: Eingänge setzen, wait until rising_edge, 1 ns warten, vergleichen.
  4. Auswertung durch die bestehenden Gates: Der GHDL-Validator führt die Vergleichs-Testbench wie jede andere aus. Eine Abweichung meldet MODEL_MISMATCH cycle=<n> port=<p> expected=<soll> got=<ist> inputs=<…> und wird als Fehlerklasse model_mismatch an die HDL-Reparatur gegeben. Die Meldung nennt Takt, Port, Soll- und Ist-Wert und ist damit präziser als „assertion failed“.
  5. Weiterleitung bei Verdacht auf ein falsches Modell: Bleibt die Abweichung nach zwei HDL-Reparaturen bestehen, wird einmalig das Modell mit der Abweichung als Hinweis überprüft und gegebenenfalls neu erzeugt (Verständnis- statt Codierungsfehler).

Was entfällt: Der Planer erzeugt keine Golden-Vektoren mehr (simulation_vectors). Vorhandene Vektoren werden nur noch informativ ausgewertet und blockieren die Abdeckung nicht. Das Feld bleibt im Schema erhalten, damit bestehende Projekte gültig bleiben.

Grenzen:

  • Der Vergleich ist taktgenau. Lässt die Spezifikation etwas offen (z. B. 30 oder 31 Takte Grünphase), legt das Modell eine Auslegung fest, die der Entwurf dann übernehmen muss. Das ist gewollt (eine verbindliche Auslegung), aber keine Prüfung gegen „die“ Spezifikation.
  • Ein falsches Modell kann einen korrekten Entwurf in die Reparatur schicken. Selbsttest und einmalige Modellprüfung mildern das, schließen es nicht aus.
  • Unterstützt werden std_logic, std_logic_vector, unsigned und signed mit Richtung in/out; sonst entfällt der Test (kein Fehler). Bei aktiver UART-Echo-Brücke entfällt er ebenfalls, da die serielle Brücke nicht modelliert wird.
  • Ohne Reset-Port müssen Modell und Entwurf denselben Anfangszustand haben.
  • Ein fehlendes oder ungültiges Modell blockiert den Lauf nie; es fehlt dann nur dieser Test.
  • Die Modellerzeugung kostet einen zusätzlichen OpenCode-Aufruf; mit dem Gratis-Modell im Probelauf über 10 min.

Dateien: Schaltungsagent/src/domain/agents/reference_model.py (Stimulus, Modell-Ausführung, Testbench), agents/verification.py (Auftrag reference_model), agents/supervisor.py (_ensure_reference_model, _refresh_model_testbench, _classify_model_mismatch, _model_mismatch_target), Fehlerklasse in agents/debug.py und repair_routing.py.

16.3 Maßnahme B: Mutationsanalyse der Testbenches

Idee: Ob eine Testsuite etwas taugt, zeigt sich daran, ob sie absichtlich eingebaute Fehler findet. Aus dem Entwurf werden deterministisch kleine Fehlervarianten (Mutanten) erzeugt, je eine Änderung. Jeder Mutant läuft gegen alle Testbenches, auch die Vergleichs-Testbench aus A.

OperatorÄnderungbildet nach
bit_flipx <= '0' ↔ '1'falscher Ausgangs-/Steuerwert, z. B. Lampe dauerhaft an
negate_conditionif c then → if not (c) thenvertauschte Verzweigung
swap_relation= ↔ /= in einer Bedingungfalscher Vergleich
change_constant± 1 → ± 2 in einer Zuweisungfalsche Zähl-/Rechenschritte
drop_transitionstate <= X; → null;fehlender Zustandsübergang, z. B. Automat bleibt hängen

Nur Code im Architekturrumpf wird verändert; Kommentare, Deklarationen und Taktflanken-Bedingungen bleiben unangetastet. Die Auswahl ist deterministisch und reihum über die Operatoren verteilt (Standard: höchstens 10 Mutanten). Mutanten, die schon an Analyse oder Elaboration scheitern, zählen nicht. Kennzahl: Mutationsquote = getötete / (getötete + überlebende) Mutanten.

Gate im MAS (Phase VALIDATING, nach Simulation, Contracts und Abdeckung):

  • Quote unter gates.min_mutation_score (Standard 0,6): Fehlerklasse weak_testbench, Weiterleitung an den VerificationAgent. Dieser erhält die überlebenden Mutanten je Modul im Auftrag („erkennt folgende fehlerhafte Varianten NICHT …“) und ergänzt gezielt Prüfungen.
  • Genau ein solcher Nachbesserungsversuch. Ist die Quote danach immer noch zu niedrig, läuft der Lauf mit Warnung weiter (MUTATION_WARNING). Grund: Äquivalente Mutanten (Änderung ohne beobachtbare Wirkung) sind nie erkennbar, und ein Gate, das einen korrekten Entwurf endlos blockiert, hatte sich bei den Golden-Vektoren als schädlich erwiesen.

Dateien: Schaltungsagent/src/domain/agents/mutation.py, agents/supervisor.py (_mutation_gate, Hinweise an die Testbench-Reparatur), agents/verification.py (Hinweise im Testbench-Auftrag), Einstellungen gates.min_mutation_score, gates.max_mutants (Dashboard).
