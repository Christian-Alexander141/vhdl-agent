# Projektbeschreibung: KI-gestützte Engineering-Agentenplattform

## Ziel

Entwickle eine modulare KI-Agentenplattform, die über ein Dashboard und einen Chat bedient wird.

Der Benutzer beschreibt eine technische Aufgabe in natürlicher Sprache. Der Agent analysiert die Aufgabe, nutzt domänenspezifisches Wissen über eine RAG-Komponente, erzeugt Dateien und kann komplexe Entwicklungsaufgaben an einen spezialisierten Coding-Agenten (OpenCode) delegieren.

Das System soll zunächst für Hardwareentwicklung mit VHDL ausgelegt werden, aber später auf andere technische Domänen erweiterbar sein.

Beispiel:

Benutzer:
"Erzeuge einen 8-Bit-Zähler in VHDL mit Testbench."

System:

1. Analysiert die Anforderungen.
2. Nutzt RAG mit internen VHDL-Standards und Beispielen.
3. Erzeugt:

   * counter.vhd
   * counter_tb.vhd
4. Speichert die Dateien in einem isolierten Workspace.
5. Übergibt die Aufgabe an OpenCode.
6. OpenCode führt Tests mit GHDL aus.
7. Bei Fehlern analysiert OpenCode die Fehler, verbessert den Code und testet erneut.
8. Das Ergebnis wird an den Chat und das Dashboard zurückgegeben.

## 2. Implementierte Komponenten

### Domain-Layer (`src/domain/`)
- `state_machine.py` — StateMachine mit 11 Zuständen: CREATED → ANALYZING → RAG_SEARCH → GENERATING_ARTIFACTS → WORKSPACE_READY → RUNNING_AGENT → TESTING → (VALIDATING|REPAIRING|COMPLETED|FAILED), Transition-Validierung, Fehler bei illegalen Übergängen
- `event_bus.py` — synchroner EventBus mit Multi-Subscriber, Event-Log, `emit_event()`, `get_events()`
- `models/` — Pydantic-Modelle: TaskState (task_id, status, request, domain, workspace, generated_files, artifacts, opencode_result, test_results, history, iterations, metadata, error_message), Event/EventType (23 Eventtypen), KnowledgeBundle, ArtifactBundle, CodingRule, ReferenceDesign, DocumentRef
- `ports/` — Interfaces: LLMService, RAGService, ArtifactGenerator, FileSystemService, OpenCodeService, EventPublisher, ValidationService, PlannerService, Tool
- `exceptions.py` — WorkflowError, RAGError, LLMError, ArtifactError, WorkspaceError, AgentExecutionError, StateMachineError
- `workflow/workflow.py` — Workflow-Klasse, enthält dieselbe Schrittfolge wie der Orchestrator (Analyse → RAG → Artifakte → Workspace → Agent/Planner → Test&Repair → Validierung)
- `domain_registry.py` — automatische Erkennung von Domain-Plugins in `src/domain_plugins/`

### Service-Layer (`src/services/`)
- `llm_service.py` — `OllamaLLMService` (echtes LLM, per config.yaml wählbar) + `StubLLMService` als Fallback; `analyze_request()`, `generate_code()`, `summarize_result()`
- `rag_service.py` — `VHDLRAGService`: Keyword/Template-Matching + Vektor-Suche, liefert KnowledgeBundle
- `rag_pipeline.py` — `RAGChatPipeline`: Qdrant Vector Store (lokaler Pfad), HuggingFace-Embeddings (Fallback all-MiniLM), Chunking 1000/200, Chat-Sessions mit Persistenz in `memory/<chat_id>/soul.md`, `query()` und `query_with_tools()`
- `artifact_generator.py` — `VHDLArtifactGenerator` mit Jinja2-Templates (counter, hamming), Entity-Namens-/Breiten-Extraktion aus dem Request, Fallback bei fehlendem Template-Match
- `filesystem_service.py` — `LocalFileSystemService`: Workspaces `projects/<task_uuid>/src|tests|docs|build|logs|reports`, TTL-Cleanup (72h), Workspace-Limit (100), `cleanup_expired()`
- `opencode_service.py` — `SubprocessOpenCodeService` (CLI `opencode run`) und `DockerOpenCodeService` (Fallback auf Subprocess bei fehlendem Docker-Socket/Binary)
- `opencode_agent_tool.py` — LangChain-Tools: `dispatch_opencode`, `read_file_tool`, `write_file_tool`
- `task_planner_service.py` — LangGraph-basierter Planner: LLM erzeugt JSON-Plan (steps), Ausführung über Tools, Abschluss-Zusammenfassung

### Infrastructure-Layer (`src/infrastructure/`)
- `validation/ghdl_validator.py` — `GHDLValidator` (Port ValidationService): führt `ghdl -a` je VHDL-Datei aus; wird aber aktuell NICHT in main.py/api_server.py verdrahtet (siehe Abschnitt "Bekannte Probleme")
- `rag/` — chunker, document_loader, embedding_provider, retriever, vector_store, context_builder, prompt_builder, memory_provider

### Orchestrator (`src/orchestrator/orchestrator.py`)
- `AsyncAgentOrchestrator`: `execute()` (synchron) und `execute_async()` (Thread + Callback)
- Schrittfolge: TASK_CREATED → Analyse (LLM) → RAG-Suche → Artifakt-Generierung → Workspace → OpenCode-Agent → Test&Repair-Loop (max. 5 Iterationen) → Validierung/Summary → COMPLETED/FAILED
- Ereignisse werden über den EventBus publiziert, State wird als `state.json` im Workspace gespeichert

### VHDL-Domain-Plugin (`src/domain_plugins/vhdl/`)
- `rag_data.py` — 4 Coding-Rules, 2 Referenzdesigns (counter, hamming), IEEE-Standards, TEMPLATE_MAP für Keyword-Matching
- `templates.py` — Jinja2-Templates: counter (entity, architecture, tb_entity, tb_architecture), hamming (decoder, testbench)
- `prompts.py` — VHDLPrompts (ANALYSIS_SYSTEM, CODE_GENERATION_SYSTEM, REPAIR_SYSTEM)
- `test_definitions.py`, `build_definitions.py` — GHDL-Test-/Build-Konfigurationen

### API, Dashboard, CLI
- `api_server.py` — FastAPI: GET `/`, `/api/tasks`, `/api/tasks/{id}`, POST `/api/task` (async), `/api/task/sync`, GET `/api/domains`, `/api/debug`, POST `/api/cleanup`, WebSocket `/ws` (Event-Broadcast + Task-Ausführung)
- `api/rag_router.py` — `/api/rag/health`, `/query` (mit/ohne Planner/Tools), `/chat`, `/index`, `/upload`, `/models`
- `dashboard/` — Vanilla-HTML/JS/CSS-Frontend (index.html, app.js, style.css)
- `main.py` — CLI: `run`, `list`, `show`, `file`, `discover`, `serve`, `rag`

## 5. Bekannte Probleme / technische Schulden

1. **GHDLValidator nicht verdrahtet**: Der `GHDLValidator` existiert, wird aber in `main.py`/`api_server.py` nicht als `validation_service` an den Orchestrator übergeben → Tests laufen aktuell über OpenCode (im Docker-Container) statt direkt über GHDL. Der OpenCode-Agent ruft GHDL selbst auf, wenn es im Container verfügbar ist.
2. **execute_async-Bug**: Die in `execute_async()` erzeugte `task_id` (UUID) stimmt nicht mit der tatsächlichen Task-ID der Ausführung überein, da `execute()` intern eine neue TaskState/UUID erzeugt → Status-Abfrage über die zurückgegebene ID findet den Task nicht.
3. **Tests nicht ausführbar**: `pytest` ist nicht im venv installiert; es existieren 37+ Tests (`src/tests/test_unit.py`, `test_architecture.py`, `test_projects.py`), die derzeit nicht laufen.
4. **Keine API-Authentifizierung**, kein Caching, keine Datenbank (Task-States nur als JSON-Dateien), keine Metriken/Monitoring, WebSocket-Endpoint läuft synchron.
5. **E-Mail-Konfiguration**: Git-Config enthält laut Commit-Log einen Test-Eintrag (c154807 "Test: E-Mail geaendert").
6. **Task-Verzeichnisse ohne state.json** (z. B. `projects/ac219d18-...`, `projects/eca8cd5a-...`) — vermutlich abgebrochene/leere Workspaces.

## 6. Nächste sinnvolle Schritte

- `GHDLValidator` in `main.py`/`api_server.py` an den Orchestrator anbinden (Tests dann direkt über GHDL statt OpenCode)
- `execute_async()`-Task-ID-Bug beheben (Task-ID vor Thread-Start erzeugen und an `execute()` durchreichen)
- `pytest` im venv installieren und Tests ausführen
- API-Auth und Caching ergänzen (siehe IMPROVEMENTS.md)

# Abläufe (Workflows, Komponenten, Container)

## 1. Docker-Container "flamboyant_vaughan" (OpenCode-Agent)

Der Schaltungsagent delegiert Implementierungs- und Testaufgaben an den OpenCode-Coding-Agenten, der isoliert in einem Docker-Container läuft.

| Eigenschaft | Wert |
|-------------|------|
| Container-Name | `flamboyant_vaughan` |
| Image | `ghcr.io/anomalyco/opencode:latest` |
| OpenCode-Version im Container | 1.18.11 (`/usr/local/bin/opencode`) |
| Start-Befehl | `docker run -d --name flamboyant_vaughan -v <repo>/projects:/projects -w /projects ghcr.io/anomalyco/opencode:latest` |
| Volume-Mount | `<repo>/projects:/projects` (bind mount, rw) |
| Arbeitsverzeichnis | `/projects` |
| Benutzername | root (Standard-Image) |

Wichtig:
- Der Mount ist **Pflicht**: Ohne ihn sieht der Container die Host-Workspaces nicht und `docker exec -w /projects/<task_id> ...` scheitert mit returncode 127 → Task wird FAILED.
- GHDL ist im Container **nicht** installiert. GHDL läuft nur auf dem Host (`/usr/bin/ghdl`, v4.1.0). Der OpenCode-Agent kann GHDL im Container daher nicht selbst ausführen; eine GHDL-basierte Validierung im Testschritt wird über den (noch nicht verdrahteten) `GHDLValidator` auf dem Host abgewickelt.
- Container-Mounts können nach dem Start nicht geändert werden → bei Änderungen muss der Container neu erstellt werden (stop, rm, run).

## 2. Vollständiger Task-Ablauf (End-to-End)

Start: CLI `python -m src.main run "<Anforderung>"` oder API `POST /api/task`.

```
CREATED
  │  1. TaskState anlegen (task_id = UUID), Event TASK_CREATED
  ▼
ANALYZING
  │  2. LLMService.analyze_request()  → strukturierte Analyse (Ollama gpt-oss:120b-cloud)
  ▼
RAG_SEARCH
  │  3. VHDLRAGService.retrieve_knowledge()
  │     - Keyword/Template-Matching (z.B. "zähler" → Template "counter")
  │     - Vektor-Suche in Qdrant (top_k=5), Kontext-Erweiterung
  ▼
GENERATING_ARTIFACTS
  │  4. VHDLArtifactGenerator.generate()
  │     - Template-Match → Jinja2-Rendering (counter/hamming)
  │     - sonst Fallback (keine Dateien)
  ▼
WORKSPACE_READY
  │  5. LocalFileSystemService.create_workspace()
  │     projects/<task_id>/src|tests|docs|build|logs|reports
  │     Artifakte werden geschrieben (src/<name>.vhd, tests/<name>_tb.vhd)
  ▼
RUNNING_AGENT
  │  6. OpenCodeService.execute() im Docker-Container
  │     docker exec -w /projects/<task_id> flamboyant_vaughan opencode run "<Instruktion>"
  │     Instruktion: "Implementiere die VHDL-Komponente im Projekt ... Anforderung: ..."
  ▼
TESTING
  │  7. Testschritt (Iteration 1..5):
  │     a) falls validation_service gesetzt: GHDLValidator (ghdl -a) → direkt auf Host
  │     b) sonst: OpenCode.execute() mit "Teste und verifiziere die VHDL-Komponente..."
  │
  ├── bestanden → VALIDATING
  │
  └── fehlgeschlagen → REPAIRING (8) → RUNNING_AGENT (6) → TESTING (7) ... max. 5 Iterationen
  ▼
VALIDATING
  │  9. LLMService.summarize_result() → Zusammenfassung ins State-Metadata
  ▼
COMPLETED  (oder FAILED, falls Fehler/Iterationslimit erreicht)
  │  10. state.json wird im Workspace gespeichert, Task-Ergebnis an CLI/API zurückgegeben
```

Dauer-Messung (real, Testlauf 10.08.2026): Analyse ~20s, RAG ~15s, OpenCode-Lauf ~36s + ~146s, Test ~2s. Gesamt ca. 4 Minuten pro Task.

## 3. Ablauf der GHDL-Simulation (Host)

Die erzeugten VHDL-Dateien werden mit GHDL auf dem Host analysiert, elaboriert und simuliert:

```bash
cd projects/<task_id>
ghdl -a src/<name>.vhd          # 1. Analyse (Syntax-Check, Bibliotheken)
ghdl -a tests/<name>_tb.vhd     # 2. Analyse der Testbench
ghdl -e <name>_tb               # 3. Elaboration (Design zusammenbauen)
ghdl -r <name>_tb --stop-time=500ns   # 4. Simulation (optional: --vcd=sim.vcd für Wellenform)
```

Erwartete Ausgabe bei Erfolg: `(assertion note): Simulation finished` und Exit-Code 0.

## 4. Pfad-Auflösung Host ↔ Container

`DockerOpenCodeService._resolve_container_path()`:

| Host-Pfad | Container-Pfad |
|-----------|----------------|
| `<repo>/projects/<task_id>` | `/projects/<task_id>` |
| `<repo>/projects` | `/projects` |

Der Host-Workspace `docker_host_workspace: ./projects` (relativ zum Startverzeichnis des Prozesses) wird mit dem Container-Verzeichnis `docker_workspace: /projects` verrechnet.

## 5. Beteiligte Systeme und ihre Rollen

| System | Rolle | Erreichbarkeit |
|--------|-------|----------------|
| **GHDL 4.1.0** (Host) | VHDL-Analyse, Elaboration, Simulation | `/usr/bin/ghdl` |
| **Ollama** | LLM-Inferenz (Analyse, Summaries) | `http://localhost:11434` |
| **Ollama-Modell** | `gpt-oss:120b-cloud` (Cloud-Modell über Ollama) | — |
| **OpenCode CLI** (Host, optional) | Fallback, wenn Docker nicht verfügbar | `/home/alex/.opencode/bin/opencode` |
| **OpenCode im Container** | Implementierung, Testausführung, Reparatur | `docker exec flamboyant_vaughan opencode run ...` |
| **Qdrant** (lokal, eingebettet) | Vektorspeicher für RAG | `./memory/qdrant` (Collection `vhdl_knowledge`) |
| **Embedding-Modell** | `jina-embeddings-v5-text-small` (Fallback: all-MiniLM-L6-v2) | HuggingFace |

## 6. Weitere Abläufe

### CLI (`python -m src.main`)
- `run "<request>"` — kompletten Task-Workflow ausführen
- `list` — alle Tasks aus `projects/*/state.json` auflisten
- `show <task_id>` — Task-Detail als JSON
- `file <task_id> <pfad>` — generierte Datei anzeigen
- `discover` — Domain-Plugins in `src/domain_plugins/` erkennen
- `serve` — FastAPI-Server + Dashboard (Standard 0.0.0.0:8088)
- `rag` — interaktiver RAG-Chat

### API-Server (FastAPI)
- Dashboard: `http://localhost:8088/` (HTML/JS, statisch)
- REST: `/api/tasks`, `/api/task` (async), `/api/task/sync`, `/api/domains`, `/api/cleanup`, `/api/debug`
- RAG-Router: `/api/rag/health`, `/api/rag/query`, `/api/rag/chat`, `/api/rag/index`, `/api/rag/upload`, `/api/rag/models`
- WebSocket: `/ws` — broadcastet alle Events (STATE_CHANGED, TEST_FAILED, TASK_COMPLETED, ...) an das Dashboard und kann selbst Tasks ausführen

### RAG-Chat (Dashboard/CLI)
1. Chat-Session erzeugen (`memory/<chat_id>/soul.md` wird angelegt)
2. Bei jeder Anfrage: Dokumente indexieren (falls leer) → Kontext aus Qdrant (top_k=5) → Gedächtnis aus soul.md → RAG-Prompt → LLM-Antwort
3. Austausch wird an soul.md angehängt (Persistenz über Sessions hinweg)
4. Optional: `useTools=true` (OpenCode-/Datei-Tools) oder `usePlanner=true` (JSON-Plan mit Steps, dann Ausführung)

### Event-Fluss zum Dashboard
```
Orchestrator → EventBus.publish() → broadcast_sync() → asyncio.run_coroutine_threadsafe()
              → WebSocket /ws → Dashboard (app.js)
```
Zusätzlich REST-Polling als Fallback (`/api/tasks`).

Das System soll NICHT als freier Chat-Agent gebaut werden.

Der Kern ist ein Workflow-Orchestrator.

Das LLM entscheidet nicht alleine über alle Aktionen.

Der Orchestrator verwaltet:

* Zustand
* Aufgabenfortschritt
* Tool-Aufrufe
* Fehlerbehandlung
* Events für das Dashboard

Der Orchestrator ist die zentrale Komponente.

Verantwortlichkeiten:

* Erzeugen einer Task-ID
* Verwalten des Zustands
* Ausführen der Workflow-Schritte
* Aufrufen der Services
* Erzeugen von Events
* Fehlerbehandlung

Beispiel Workflow:

```
CREATED

↓

ANALYZING

↓

RAG_GENERATING

↓

FILES_CREATED

↓

TESTING

↓

REPAIRING

↓

COMPLETED
```

Der Orchestrator soll keine konkrete Implementierung von RAG oder OpenCode kennen.

# 8. OpenCode Service

OpenCode wird als spezialisierter Entwicklungsagent verwendet.

Nicht für einfache Dateioperationen.

OpenCode Aufgaben:

* Projektanalyse
* Kompilieren
* Testen
* Debugging
* Refactoring

Beispiel Auftrag:

```
Arbeite im Workspace.

Führe VHDL Tests aus.

Verwende:

ghdl -a
ghdl -e
ghdl -r

Analysiere Fehler.

Verbessere den Code.

Wiederhole maximal fünf Iterationen.

Erstelle einen Bericht.
```

OpenCode läuft später isoliert:

* Container
* eingeschränkte Rechte
* Logging
